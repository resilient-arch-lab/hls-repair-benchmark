# HLS Repair Benchmark — Artifact

Reproduction package for:

**Maisha Mastora and Dean Sullivan.**  
*Executable HLS Bug Repair: Benchmarking LLM-Based Automated Program Repair
for High-Level Synthesis.*  
2026 IEEE International Conference on Computer Design (ICCD 2026).

---

## What this studies

We construct the **first executable HLS bug-repair benchmark** by combining:

- **Chrysalis-HLS** — 1 500+ function-level bug specifications (JSON diffs)
  for CHStone HLS programs, covering 8 bug types.
- **CHStone** — HLS benchmark suite whose `main()` functions double as
  self-checking execution oracles (exit code 0 = correct, non-zero = buggy).

The result is **41 executable HLS instances** where every candidate patch
can be validated by compile-and-run, with no testbench authorship required.

### Key findings (GPT-4o, 5 runs per instance)

| Metric | Value |
|--------|-------|
| Repair rate | 25.9 % |
| Compile rate | 72.0 % |
| Solution multiplicity | 0.932 |

- 54.1 % of HLS patches compile but fail the oracle — the execution oracle
  is essential; a diff-based check would massively overestimate repair.

## Quick start

## Reproducing from pre-built results

The `results/` directory contains the exact JSON outputs from our GPT-4o
runs (September 2026). To reproduce the paper's statistics without re-running
the LLM:

```python
import json, numpy as np

hls = json.load(open("results/hls_results_full.json"))

hls_rates = [r["repair_success_rate"] for r in hls if "repair_success_rate" in r]
hls_mult  = [r["solution_multiplicity"] for r in hls if "solution_multiplicity" in r]

print("Repair rate:          ", f"{sum(hls_rates)/len(hls_rates):.3f}")
print("Solution multiplicity:", f"{sum(hls_mult)/len(hls_mult):.3f}")
print("Instances:            ", len(hls_rates))
```

## Creating repair using APIs

```bash
# 1. Clone this repo
git clone https://github.com/mmastora933/hls-repair-benchmark.git
cd hls-repair-benchmark

# 2. Fetch dependencies and build benchmark instances
bash setup.sh
#   → benchmarks/hls/benchmark_meta.json  (41 instances)

# 3. Run LLM repair experiments (requires OPENAI_API_KEY)
export OPENAI_API_KEY=sk-...
python3 scripts/run_hls_repair.py --n_runs 5 --output results/hls_results.json
```

`run_hls_repair.py` checkpoints after every instance, so it can be safely
interrupted and resumed with `--start_from N`.

## Why CHStone source is not included

CHStone has no top-level `LICENSE` file; each benchmark carries individual
program copyrights. Out of caution we do not redistribute the source.
`setup.sh` clones it from `github.com/t-crest/patmos-hls` (~45 MB,
takes ~1 min). If that URL ever changes, any CHStone clone works; set
`CHSTONE_DIR` before running `inject_bugs.py`.

## Oracle design

```
inject_bugs.py:
  for each Chrysalis bug spec (single-edit):
    1. copy CHStone/<bench>/ → correct/
    2. copy CHStone/<bench>/ → buggy/ ; apply JSON diff
    3. gcc -O0 -o bin correct/<entry>.c -lm && ./bin → must exit 0
    4. gcc -O0 -o bin buggy/<entry>.c  -lm && ./bin → must exit ≠ 0
    5. if both checks pass → instance accepted

validate_hls.py (called during repair):
    1. copy buggy/ to tmpdir
    2. replace target_file with LLM patch
    3. gcc -O0 -o bin <entry>.c -lm && ./bin → exit 0 = PASS
```

Key insight: each CHStone benchmark compiles via **one entry `.c` file**
that `#include`s the rest. Compiling `*.c` directly causes duplicate-symbol
errors. `inject_bugs.py` encodes the entry file for each benchmark in
`BENCH_ENTRY_FILE`.

## Oracle sensitivity

Not all Chrysalis specs produce accepted instances. The main rejection
reasons (logged to stdout by `inject_bugs.py`):

| Reason | Fraction of attempted |
|--------|----------------------|
| Bug not detected by oracle (insufficient code coverage) | ~71 % |
| Original code not found in CHStone | ~15 % |
| Correct version fails to compile/run | ~8 % |
| Other (injection failure, unsupported benchmark) | ~6 % |

The CHStone oracles exercise single test vectors; bugs that only manifest
with other inputs are not detected. This is a **known limitation** and
a direction for future work (mutation-aware test generation).
